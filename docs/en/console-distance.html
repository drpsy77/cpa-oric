CP/A remote console

A remote computer (or a phone's browser) types and reads in place of the real Oric's keyboard and screen, through the LOCI and its WiFi modem. Done, tested in Oricutron and on the real Oric. Specification: docs/en/console-distance.md; user guide: docs/en/manuel.md, "Remote console: REMOTE".

Short answers

Who is in charge? For the screen, the remote computer leads: its daemon (tools/remote.py) asks, the Oric only answers. The Oric never sends anything of its own accord: with no daemon, it stays silent.

Who finds the changed rows? The daemon. It keeps a copy of the 28 rows (and of the character set) and computes their checksums itself. It asks for the Oric's (S), compares, then asks for the rows that differ: one by one (L n), or all at once from 3 on (L n+$80: rows n to 27 in a row). The Oric keeps nothing of what it has sent.

When? After typing (4 keys at most), the daemon first asks for the cursor row (fast echo, 0.21 s measured), then a full cycle. When idle, one cycle every 0.5 s; straight away again as long as a cycle finds changes.

No local echo: a key typed on the computer or the phone does not show there by itself. It goes to the Oric, whose program decides what to display, and the page shows what the Oric displayed, like telnet or ssh. Key from the phone or from the Oric's keyboard: the page simply sees the Oric's screen.

Two-way? The TCP link stays open both ways while the console is on. Computer → Oric: keys and requests, whenever it likes. Oric → Computer: answers only (S, L, C frames).

Fidelity: the copy holds the exact bytes of SCREEN, attributes included, and in text mode the character set itself ($B400-$BB7F): sprites, tiles and the EDSPRITE grid appear as they are. The page draws by the ULA's rules, with pixels 1.23 times wider than tall as on a PAL TV set, and the cursor from the S frame.

Nothing is lost: a key is only read if there is room in the keyboard buffer; otherwise it waits in the LOCI, the Pico, then TCP. A text of several KB pasted into EDIT arrives at EDIT's pace.

Limits: a state shorter than a cycle is never seen (only the final state arrives). Full-screen HIRES is not sent; in SPLIT, only rows 16 to 27.

About one exchange in ten is still delayed by 1 to 2 s: a packet lost on the WiFi, resent by the Pico's TCP stack.

What changed:

  • Pico firmware: it reads everything waiting on the USB (one byte per loop turn capped it at ~650 bytes/s).
  • Per-IRQ caps depending on the port: LOCI 16 bytes received and 64 sent (a whole S frame per IRQ); a real 6551 keeps 4 and 24. Adjustable with DEBUG at $FD23-$FD26.
  • Checksums computed as the bytes are sent (~1.2 ms per row, 6 rows per IRQ at most): no buffer.
  • Grouped request L n+$80: a single round trip for a scrolling screen.
  • Fast echo kept for typing (4 keys at most), not for pasted text.
  • Daemon timings: 3 s before asking again (the modem sometimes holds back sending for more than a second), immediate TCP acknowledgement under Linux.
  • Web page with long polling: it does not poll, the daemon answers as soon as a row changes, with the changed rows only.

Gateway to the Web

To show the Oric to others (a forum), a public server serves the page over HTTPS and only lets reading through. It reaches the daemon through an encrypted tunnel (WireGuard) opened from home: the home router opens no port.

viewer --HTTPS--> public server (Apache) --tunnel--> daemon :8040 --> Oric

  • Read only, twice over: the server refuses everything but GET and HEAD, as well as /journal and /version; the daemon treats everything coming from the tunnel as a viewer (403 on sends), whatever the server's settings.
  • A call "from the Oric" coming through the tunnel is refused: nobody can pretend to be it.
  • Viewers are counted (shown on the page's status line) and capped at 40 (503 beyond, the page tries again).
  • The showcase (tools/vitrine.py), on the daemon's machine, types on the Oric as someone using it would, so that viewers see CP/A move; it pauses for 2 minutes as soon as a person types from home.

Messages exchanged

The daemon's loop (remote.py)

copy[0..27]  = 28 rows of 40 bytes ; charset[0..47] = 48 rows of 40 bytes ($B400-$BB7F)
loop:
    keys waiting (1,024 at most): send them, $FE k for each
        4 keys at most (typing, not pasted text):
            fast echo: $FD 'L' cy (cursor row, from the last S frame) -> copy[cy]
    $FD 'S' ; wait for the S frame (3 s, plus 0.1 s per key beyond 4; otherwise ask again;
              5 s without a valid frame: link lost)
    changed = rows n whose received checksum != fletcher(copy[n])
              (full-screen HIRES: none; SPLIT: 16 to 27 only)
    3 changed or more, and at least a quarter of rows n0 to 27:
        $FD 'L' (n0+$80): rows n0 to 27 arrive in a row, with no other request
    otherwise, for each: $FD 'L' n -> copy[n]
    in text mode, the character set:
        the first time: $FD 'L' (28+$80), its 48 rows in a row
        then: $FD 'C' n on the hot slices (changed less than 10 s ago)
              and two others in turn; changed slice: its rows by L
    something changed: start again straight away
    otherwise: wait 0.5 s, or the next key
the page waits on GET /ecran (long polling, 5 s at most) and only receives the changed rows

Bytes: $FE k key · $FD 'S' checksum request · $FD 'L' n row n (0-27 screen, 28-75 character set) · $FD 'L' n+$80 rows n onwards, in a row · $FD 'C' n checksums of character-set rows n to n+7 · $FD 'B' warm start · answers $FF type length data checksum. The modem only sends ASCII: a byte that does not follow $FD or $FE is ignored (NO CARRIER is never taken for typing).
